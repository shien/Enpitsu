# tdd — Red → Green → Refactor

Enpitsu ではテスト駆動開発が必須（CLAUDE.md）。**実装より先にテストを書く。** いきなり実装コードを書いてはならない。

## サイクル

### 1. Red — 失敗するテストを書く

- 期待する振る舞いをテストで定義する。バグ修正の場合は、バグを再現する回帰テストを書く。
- **動作確認:** `cargo test <test_name>` を実行し、新しいテストが**失敗する**ことを確認する。
  - コンパイルエラーによる失敗も Red として有効（未実装の関数を呼ぶ場合など）。
  - 失敗を確認せずに実装へ進んではならない。最初から通ってしまう場合、テストが振る舞いを検証できていない。

### 2. Green — 最小限の実装で通す

- テストを通す最小限の実装だけを書く。先回りの抽象化・機能追加をしない。
- **動作確認:** `cargo test` を実行し、新しいテストを含む**全テスト**が通ることを確認する。

### 3. Refactor — 整理する

- テストが通る状態を保ったままコードを整理する。
- **動作確認:** `cargo test` が全て通り、`cargo clippy -- -D warnings` と `cargo fmt -- --check` が指摘ゼロであること（`/verify` スキル参照）。

## テストの書き方（リポジトリ規約）

- ユニットテストは対象モジュールと同じファイル内の `#[cfg(test)] mod tests { ... }` に置く。結合テストは `tests/` に置く。
- テスト関数名は `snake_case` で挙動を簡潔に表す。良い例: `sokuon_kk`, `n_before_consonant`。悪い例: `test1`, `it_works`。
- カテゴリごとにコメントで区切る: `// === 促音（っ） ===`
- `assert_eq!(actual, expected)` — 期待値を右辺に書く。
- 新機能には最低限、正常系・エッジケース（空入力、境界値）・その機能固有の特殊ケースのテストを含める。

## 着手前の計画

作業開始前に、各フェーズ（Red / Green / Refactor）で「何をどう確認するか」（実行するコマンドと期待する結果）を書き出してから始めること。`plan/` にフェーズドキュメントを書く場合は `/plan-doc` スキルの規約に従う。
