# plan-status — 計画ドキュメントのステータス管理

`plan/` のフェーズ計画は、**実装が進むと実態とズレる**。このSkillはズレをなくすためのルールとフォーマットをまとめる。ステータスを書く・更新するときは必ずこれに従う。

**大原則: ドキュメントの記述を信用せず、コードで裏を取ってからステータスを書く。** 「前提: Phase 3 で trait 定義済み」のような記述が実際には未実装、という食い違いが実際に起きている。

## ステータスバナーのフォーマット

各フェーズ計画ファイル（`phaseN-*.md`）の H1 直後に、blockquote で1つだけ置く:

```markdown
# Phase N: タイトル

> **状態: <絵文字> <ラベル>（YYYY-MM 時点）**
> 実装済みの内容（対応するファイルを `src/xxx.rs` の形で示す）。
> 未対応の内容（残タスクとどのタスク番号か）。

## 目標
```

- 日付は「YYYY-MM 時点」で書く（`currentDate` を使う）。
- 実装済み・未対応を必ず両方書き、**根拠となるファイル/シンボル名**を添える（例: `src/config.rs` の `keybind_preset`）。
- 断定の前に確認する（下記「確認手順」）。

### ステータスの語彙（絵文字は統一する）

| 絵文字 | ラベル | 意味 |
|-------|-------|------|
| `✅` | 完了 | フェーズの完了条件をすべて満たす |
| `✅` | ほぼ完了 | 主要タスク完了、些末な残タスクのみ（残タスクを明記） |
| `⚠️` | 一部完了 | 一部のみ実装。当初計画と実装方式が違う場合もここ（差分を明記） |
| `⬜` | 未着手 | コードなし。ドキュメントのみ存在 |

## 同期すべき3か所（1つ直したら必ず全部見る）

ステータスは3か所に分散している。1か所だけ直すと再びズレるので**セットで更新**する:

1. **各 `phaseN-*.md` の冒頭バナー**（上記フォーマット）
2. **`plan/README.md` の「現在の状態」チェックリスト** — `[x]`（完了）/ `[~]`（一部）/ `[ ]`（未着手）と、全テスト数（`cargo test` の passed 数）
3. **`plan/README.md` の「フェーズ一覧」テーブル** — 「状態」列の絵文字ラベルをバナーと一致させる

さらに、`⚠️`/`✅ほぼ完了` のフェーズは README に **「Phase N の残タスク」節**を設け、未対応項目を箇条書きにする。

## 確認手順（ステータスを書く前に必ず実行）

実装の有無をコードで確認してから状態を決める。例:

```sh
# 想定ファイル・シンボルが実在するか
ls src/ | grep -i <keyword>
grep -rl "ConversionBackend\|keybind_preset\|load_from_files" src/

# 依存 crate が入っているか（Phase 7 の lindera 等）
grep -c "<crate名>" Cargo.toml

# 全テスト数（README の数値更新に使う）
cargo test 2>&1 | grep "test result"
```

- **想定と実装方式が違わないか**を特に見る（例: Phase 5 は「ポップアップ窓」計画だが実装はインライン表示 → `⚠️ 一部完了`）。
- ドキュメント内の「前提」「ファイル構成 (予定)」に実態と矛盾があれば、その場で訂正する（誤った前提を残さない）。

## 未着手フェーズの前提の扱い

未実装の trait・関数を「定義済み」と書いている前提記述を見つけたら、`⬜ 未着手` バナーで実態を述べたうえで、本文を「本フェーズで新規定義する」に直す。過去の計画時点の想定をそのまま残さない。

## コミット

- ドキュメントのみの変更ならコードのテストは不要だが、README のテスト数を更新した場合はその数字が `cargo test` の実測と一致していることを確認する。
- コミットメッセージは `docs(plan): ...` プレフィックスにし、何を実態に同期したかを箇条書きで書く。
