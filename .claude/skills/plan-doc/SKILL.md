# plan-doc — 開発計画ドキュメントの作成

`plan/` フォルダのドキュメントは決まった構成に従う。新しい計画を書くとき・既存計画を更新するときはこの規約を守る。

## ファイル命名

- フェーズ計画: `phaseN-<topic>.md`（例: `phase5-candidate-ui.md`, `phase7.5-emacs-keybind.md`）
- バグ修正計画: `bugN-<topic>.md`（例: `bug3-composing-arrow-keys.md`）
- 調査メモ: `investigation-<topic>.md`
- 仕様書: `specification.md`（実装済みフェーズの仕様を集約）

## フェーズ計画の構成

既存の `plan/phase7.5-emacs-keybind.md` を手本にする。セクション構成:

```markdown
# Phase N: タイトル

## 目標
（このフェーズで達成すること。2〜4行）

## 背景
（なぜ必要か。設計上の判断があればここで説明）

## 前提
（依存する既存機能・完了済みフェーズ）

## タスク

### N.1 タスク名
（説明とチェックリスト）
- [ ] 具体的な作業項目
（必要なら想定コードのスケッチ）

**動作確認:**
- 実行するコマンドと期待する結果を具体的に書く
  （例: `cargo test preset_none_all_disabled` がパスすること）

### N.2 テストの追加
（TDD に従い、テスト一覧を実装タスクとして明記する）

## 実装順序
（タスクの依存関係と着手順）

## 完了条件
（フェーズ完了を判定できる条件のリスト。「cargo test が全て通る」を必ず含める）

## ファイル構成 (変更対象)
（変更・追加するファイルの一覧）
```

## 必須ルール

- **各タスクに「動作確認:」セクションを設ける**（CLAUDE.md のルール）。実行するコマンド、期待する結果、手動確認の内容を具体的に書く。Windows 手動テストはメモ帳（notepad.exe）+ DebugView（`[Enpitsu]` フィルタ）を使う。
- テストを実装より先に書く TDD の順序が計画に反映されていること（テスト追加タスクを実装タスクと並べて明記する）。
- ドキュメントは日本語で書く。

## plan/README.md の更新

計画ドキュメントを追加・完了したら `plan/README.md` も更新する:

- 「フェーズ一覧」テーブルに行を追加（フェーズ名はドキュメントへの相対リンクにする）
- フェーズ完了時は「現在の状態」のチェックボックスを `[x]` にし、テスト数を記載する
